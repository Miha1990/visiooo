# Визитка — локальное приложение

Реализованы первая вертикаль D01–D05 и функциональность D06–D07: аккаунт, рабочее пространство, редактор по JSON Schema, приватные фото, три шаблона, восстановление доступа, черновики, снимки публикации, QR PNG и vCard. Добавлены подтверждение почты, проверка срока подписки, квоты и административная блокировка. Это локальная версия; визуальная приёмка D06 и проверка телефонов ещё впереди.

## Быстрый запуск на Windows

Повторная незавершённая регистрация не блокируется на час только из-за существующей заявки. Повтор формы в том же браузере в течение минуты переводит к вводу уже отправленного кода; после минуты запрашивает новый. В другом браузере можно начать заново после минутного интервала: тогда нужны новый код и новая сессия, прежняя попытка больше не подтверждается. Сохраняются общие для почты ограничения: до пяти писем и пяти попыток ввода кода за часовое окно. Повтор формы, смена браузера и переотправка не сбрасывают эти счётчики. После окончания окна новый код снова доступен. Уже созданный аккаунт повторно не регистрируется.

Нужны Python 3.14 и Docker Desktop с Linux containers. Команды выполняются из корня репозитория `F:\web\myQR`.

```powershell
powershell -ExecutionPolicy Bypass -File ops/start.ps1
```

Скрипт создаёт `.venv`, устанавливает зафиксированные зависимости, создаёт `app/.env` со случайным секретом, запускает PostgreSQL 17 на локальном порту 5437, применяет миграции и запускает приложение. Данные PostgreSQL сохраняются в Docker volume. Указанный в compose пароль предназначен только для локального окружения; порт доступен только на loopback.

Без Docker доступен режим SQLite для проверки интерфейса и последовательных сценариев:

```powershell
powershell -ExecutionPolicy Bypass -File ops/start.ps1 -SQLite
```

Открыть http://127.0.0.1:8000. SQLite не заменяет PostgreSQL для проверки конкурентных квот и блокировок.

## Тестовая опубликованная визитка

В другом PowerShell, из корня репозитория:

```powershell
$env:DEBUG = 'true'
# При работе с PostgreSQL задайте ту же базу, что использует сервер:
# $env:DATABASE_URL = 'postgresql://vizitka:local-vizitka-only@127.0.0.1:5437/vizitka'
.\.venv\Scripts\python.exe app/manage.py seed_demo
```

Команда печатает случайный пароль, ссылку на опубликованную страницу, редактор и QR. Email по умолчанию — `demo@example.test`. Войдите с выданным паролем и откройте редактор. Команда даёт только этому локальному демо-аккаунту подтверждённую почту и тестовый Pro на 30 дней. Существующие аккаунты она не меняет. При `DEBUG=false`, `ENVIRONMENT` отличном от `local` или нелокальном `PUBLIC_BASE_URL` выполнение запрещено. Это фикстура разработки, не платёж и не бесплатный тариф.

Новый зарегистрированный пользователь получает один закрытый черновик, без оплаченного доступа. Письмо подтверждения выводится в терминал сервера. GET ссылки показывает страницу подтверждения; только POST расходует токен. До оплаты и подтверждения почты публикация запрещена на сервере.

## Ручная установка

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
Copy-Item app/.env.example app/.env
# Заполните SECRET_KEY случайным значением; выберите DATABASE_URL.
$env:DEBUG = 'true'
docker compose up -d --wait db
.\.venv\Scripts\python.exe app/manage.py migrate
.\.venv\Scripts\python.exe app/manage.py runserver
```

Параметры окружения PowerShell имеют приоритет над `app/.env`. Для отключения PostgreSQL в текущем окне установите `$env:DATABASE_URL = ''`. Скрипт запуска явно выбирает локальную базу. Сервер разработки не предназначен для публичного доступа.

## Проверки

```powershell
$env:DEBUG = 'true'
.\.venv\Scripts\python.exe app/manage.py test tests
.\.venv\Scripts\python.exe app/manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe app/manage.py check
Invoke-RestMethod http://127.0.0.1:8000/health/ready
```

CI запускает тесты с PostgreSQL 17, проверяет миграции и Django deployment checks. Для локального PostgreSQL тесты используют отдельную базу `test_vizitka`; пользователь БД должен иметь CREATEDB. Не направляйте тесты на рабочую БД.

Проверяются изоляция двух аккаунтов на всех маршрутах владельца, неизменность снимков, конфликты версий, квоты, блокировка, окончание подписки, CSRF, токены, URL, QR PNG и UTF-8 vCard. Конкурентные тесты запускаются только с PostgreSQL.

## Фото и оформление

Оформление разделено на три независимых блока: **Фон**, **Фото**, **Шапка**. Фон располагается под всей карточкой, фото — в блоке профиля, шапка — в верхнем баннере. Для каждого блока есть собственные загрузка, замена, просмотр текущего изображения и удаление. Можно использовать три разных фотографии одновременно. Все три сохраняются в черновике, поддерживаются всеми шаблонами и публикуются общим снимком. Для шапки используется `headerAssetId` и назначение загрузки `target=header`; ограничения и квоты общие с остальными изображениями.

В форме появился раздел «Соцсети и сайт»: Instagram, Threads, Telegram, VK, OK, MAX, Avito и сайт. Указывайте ссылки на профиль/канал/магазин целиком. Пустые поля не отображаются на визитке. Значки лежат в `app/static/icons/`, источники перечислены в `SOURCES.md` этой директории. Поле сайта совместимо с существующими визитками и экспортом vCard. Дополнительные ссылки по-прежнему доступны отдельно.

Отдельная форма «Фон визитки» загружает фото на фон всей карточки. Фон и фото профиля заменяются и убираются независимо. Фон, как и фото профиля, проходит декодирование, удаление метаданных и общую проверку квоты. Текст располагается на светлой подложке. Новые ссылки и фон видны посетителю только после публикации; QR остаётся прежним.

В редакторе доступны «Классический», «Минимализм» и «Профиль». Предпросмотр и публичная страница используют одну разметку и общие стили. На телефоне есть переключатель между формой и предпросмотром; поля и оформление обновляются при вводе.

Фото загружается отдельной формой: сначала сохраните текстовые правки. Разрешены фактически декодируемые JPEG, PNG и WebP до 5 МБ и 20 мегапикселей; анимация запрещена. Сервер учитывает ориентацию, уменьшает фото до 1600 × 1600, перекодирует в WebP и удаляет метаданные. MIME и имя файла не считаются подтверждением формата.

Локальные файлы находятся в `app/private-media/` под случайными именами, за пределами static. Не настраивайте публичную раздачу этой директории. Изображения выдаются через контролируемые маршруты. Публично доступно только фото текущего опубликованного снимка, с проверкой блокировки, публикации и подписки. При скрытии визитки все её публичные изображения возвращают 404. Замена или удаление фото из черновика не меняет публичный снимок до публикации.

Неиспользуемые файлы удаляются после успешного изменения визитки. Сохраняются изображения всех текущих черновиков и опубликованных снимков, включая временно скрытые визитки. Старые снимки не резервируют файлы, которые больше нигде не используются. Квоты: 10 МБ до оплаты, 50 МБ с активным Профи; учитывается размер используемых перекодированных файлов, а при замене — освобождение старого неопубликованного изображения. Очистка и запись ссылок на фото используют общую блокировку рабочего пространства; откат транзакции отменяет очистку. Накопившиеся файлы очищает `python manage.py cleanup_unused_assets` (предварительный просмотр — `--dry-run`); команда включена в обновление сервера. Ошибка удаления оставляет файл и запись для повторной попытки.

## Восстановление пароля

Ссылка «Не помню пароль» на странице входа ведёт на `/accounts/password-reset`. Ответ одинаков для существующего и неизвестного email; письма локально видны в терминале. Ссылка действует один час, GET не расходует токен, POST с CSRF проверяет новый пароль и использует токен один раз. В базе хранятся хеш токена и отпечаток текущего хеша пароля. Смена пароля делает остальные ссылки восстановления и старые сессии недействительными. После восстановления нужно войти заново; подтверждение email по-прежнему выполняется отдельно.

## Фото ↔ QR и физические визитки

Нажмите фото профиля (или инициалы) на опубликованной визитке: появится увеличенный QR со ссылкой на эту электронную визитку. Нажмите ещё раз, чтобы вернуть фото. Сканирование открывает страницу с кнопкой «Сохранить контакт». В предпросмотре работает тот же переключатель, но неопубликованная ссылка для посетителя по-прежнему закрыта.

В кабинете и редакторе появилась ссылка «Физические визитки QR / NFC». Создайте носитель, выберите свою электронную визитку и скачайте QR PNG. В NFC нужно записать **ту же** постоянную ссылку вида `/p/{public_id}`. При перепривязке назначение меняется на сервере сразу, а QR и содержимое чипа остаются прежними. Отключение или отсутствие назначения даёт 404. Скрытие, блокировка, удаление целевой визитки и истечение Pro закрывают переход. До публикации можно подготовить носитель, но посетитель не увидит черновик.

Запись прямо из браузера рассчитана на поддерживаемые телефоны с Web NFC/NDEF: https://developer.chrome.com/docs/capabilities/nfc. Кнопка требует согласия на замену предыдущей записи; можно отменить ожидание. Если API недоступен, скопируйте ссылку и запишите её как URL отдельным NFC-приложением. Нужна перезаписываемая NDEF-метка. Приложение не блокирует чип от дальнейшей записи. Локальный loopback-адрес не записывается: для реальных NFC/QR сначала нужен публичный домен и HTTPS. На физическом телефоне запись ещё не проверена.

Доступно до 20 носителей на пространство, отключённые ссылки сохраняются и могут использоваться повторно с новым назначением. История изменений показана владельцу. Реальная NFC-метка не создаётся программой: пользователь предоставляет карточку и выполняет запись на своём телефоне. Миграция `cards/0003_physicalcard_physicalcardevent` применяется обычной командой migrate.

## Свой домен

В кабинете и редакторе доступен раздел **Свой домен** (`/app/domains`). Введите принадлежащий вам домен, выберите визитку, создайте TXT/A по инструкции, подтвердите DNS и запросите HTTPS. Домен открывает выбранную визитку на главной странице; назначение можно поменять. Исходные ссылки и QR/NFC платформы сохраняются. Один домен на рабочее пространство; клиентский домен не даёт доступа к кабинету или чужим визиткам.

Реализация основана на SPCh: отдельный Nginx/Certbot worker с очередью и heartbeat. Локально можно подготовить привязку; пока не настроены публичный IP и серверный сервис, проверка DNS/выпуск HTTPS недоступны. Инструкция администратора и systemd-шаблоны — [`ops/DOMAINS.md`](../ops/DOMAINS.md). На этой машине реальные DNS, Nginx и сертификаты не изменялись. Миграция: `domains/0001_initial`.

## Основные маршруты

- `/` — главная; `/pricing` — тариф.
- `/accounts/register`, `/accounts/login` — аккаунт.
- `/app/physical-cards` — физические визитки, `/p/{public_id}` — переход по QR/NFC.
- `/c/{public_id}/qr.png` — публичный QR для переключателя фото.
- `/accounts/password-reset` — восстановление пароля.
- `/app/assets` — POST загрузки фото; `/app/cards/{uuid}/assets/{asset_uuid}` — фото черновика для владельца.
- `/c/{public_id}/assets/{asset_uuid}` — фото текущего опубликованного снимка.
- `/app/cards` — кабинет; `/app/cards/{uuid}/edit` — редактор, предпросмотр и QR.
- `/c/{public_id}` — публичная версия; `/c/{public_id}/contact.vcf` — контакт.
- `/health/live`, `/health/ready` — процесс и соединение с БД.
- `/admin/` — админка; пользователя создают через `python app/manage.py createsuperuser`.

Публичные ответы не кэшируются и запрещают индексацию. Изменения черновика не меняют опубликованную версию до повторной публикации. При снятии с публикации, блокировке или окончании Pro HTML и vCard возвращают нейтральный 404. QR содержит постоянный адрес платформы. Удалённые public_id сохраняются в виде tombstone и никогда не назначаются новой визитке.

## Что остаётся по плану

- D05: проверить QR камерой и импорт vCard на реальных iOS/Android; автоматические проверки формата не подтверждают импорт на устройствах.
- D06: функциональность фото и трёх шаблонов готова; нужна визуальная проверка адаптивности в браузере.
- D07: подтверждение email и восстановление пароля реализованы; перед размещением нужен настроенный SMTP.
- D08: жалобы, полный журнал модерации и общая защита частоты для нескольких процессов; локальный throttle работает только в одном процессе.
- D09: тестовый сервер, HTTPS, SMTP, резервирование, мониторинг, проверка восстановления, 2FA администратора.
- D11: ядро доступа и квоты готовы; нужен полный эксплуатационный сценарий подписок.
- D12–D15: тестовая ЮKassa и сверка, статистика, пилот и подготовка запуска. Код клиентских доменов готов; нужны установка серверного обработчика и проверка реальных DNS/TLS, а смена основного домена платформы из админки остаётся отдельной задачей.

Клиентские домены можно подготовить в кабинете; реальное открытие требует настроенного публичного сервера. Маршрутов оплаты пока нет, реальные деньги не списываются. Цены на странице — гипотеза из ТЗ. Хостинг, провайдеры и юридические документы требуют отдельной настройки владельцем. До публичного запуска также нужны проверка уязвимостей зависимостей, production WSGI-сервер, раздача static, общая база throttle, резервные копии и нагрузочная проверка.
